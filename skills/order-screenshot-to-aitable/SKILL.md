# 订单截图入多维表

接收使用者提供的订单截图和承接助教姓名，把订单信息录入钉钉 AI 表格。整个流程围绕一条底线设计：**只能新增，绝不修改或删除表里已有内容**。

## 输入

每次执行需要两样东西：

1. **订单截图**，一张或多张。多张时按订单编号合并成一批。
2. **承接助教姓名**，由本次使用者明确打出。例如"这批给张老师"。

助教姓名是必填输入。没有拿到就停下来问，不要沿用上一次的值，也不要猜。

### 缺少助教姓名时必须追问

只收到截图、没收到助教姓名时，**先问，不要先做**。追问期间不要进入写入流程的任何一步，也不要"先把能填的填上"。

追问示例：

> 收到截图了。请告诉我这批订单分配给哪位助教来承接，我再录入。

以下两种情形同样按追问处理：

- 名字在当前组织里查不到。
- 名字没有完全匹配（例如只写了姓氏或简称，系统语义匹配到某个全名）。这种情况必须让使用者确认全名，不要自行采用相似结果。

脚本会把这两种情况标为 `next_action: ask_user_for_assistant`，看到这个信号就停下来问人。

使用者给出姓名后再从头执行第 0 步，不要跳过预检。

## 铁律

以下约束优先于任何效率要求。使用者要求"顺便改一下""覆盖掉旧的"时，停下来确认，不要自行执行。

1. **唯一允许的写命令是 `dws aitable record create`。**
2. **禁止** `record update`、`record delete`、`field create`、`field update`、`field delete`、`table update`、`table delete`、`base update`、`base delete`、`advperm-*`，以及任何导入覆盖类操作。
3. **承接助教必须来自本次使用者的指定**，通过 `--assistant` 传入。绝不静默使用配置里的默认值；配置默认值只作为示例记录在案。缺少姓名或姓名非完全匹配时一律追问，不得先录入。
4. **订单编号字段必须是文本类型。** 数字类型会把 19 位订单号四舍五入且不可逆。预检不通过就停止。
5. **已存在的订单一律跳过**，不更新、不覆盖、不补全。
6. **每次写入前 capture、写入后 verify。** verify 报错必须原样上报。
7. **不改表结构、不改字段配置、不改视图、不改权限。** 发现历史数据有问题只报告，不动手。

## 目标表

配置在 `references/target-table.json`：包含 baseId、tableId、视图、字段 ID 与类型要求。

换组织或换表时只改这个文件；字段 ID 必须来自实时 `field get`。

首次使用先复制示例配置，再填入你自己的信息：

```bash
cp references/target-table.example.json references/target-table.json
```

`target-table.json` 属于本地私有配置，不要提交到公开仓库。

| 内容 | 字段 | 写入要求 |
|---|---|---|
| 订单编号 | 订单编号（文本） | 19 位原样保留 |
| 下单时间 | 用户下单日期（日期） | `YYYY-MM-DD HH:mm:ss` |
| 收货号码 | 虚拟手机号（文本） | 形如 `17851404569 [2079]` |
| 承接助教 | 承接助教（人员） | `userId` + `corpId`，来自实时解析 |

只读字段不可写：「进量编号」「发货地址」「发货备注」「核销码」。

收货人姓名没有对应字段，只用于核对号码归属，不单独写入。

## 执行流程

### 第 0 步：预检

```bash
python3 scripts/preflight_check.py --assistant "<本次助教姓名>"
```

校验登录态、订单编号字段类型、目标字段可写性、助教身份、目标表存在性。

`ok=false` 时停止并把 `blockers` 原文交给使用者。助教名字打错或不在本组织时，这里就会拦住。

### 第 1 步：读图提取

按 `references/extraction-rules.md` 提取。要点：点闭眼图标拿到后缀，悬停虚拟号拿到完整号码，用商品单ID 与订单编号交叉核对。

多张截图合并成一个 JSON 文件。重复出现的订单只保留一条。看不清的数字留空，不要猜。

### 第 2 步：校验与去重

```bash
python3 scripts/validate_records.py \
  --input <提取结果>.json \
  --assistant "<本次助教姓名>" \
  --check-table \
  --out /tmp/order-write.json
```

校验位数、交叉核对、时间格式、号码格式、批内重复，并批量查询排除已存在的订单。

看三个字段：

- `ok=true` 才能进入写入。
- `fatal` 非空时**必须停止**，不能写入。
- `blocked_records` 列出被拦下的记录及原因，需要逐条反馈给使用者。

`--assistant` 是必填的。不传会直接拒绝执行，避免把订单记到错误的人名下。

默认策略是写入有效记录、把有问题的记录单独列出来；加 `--require-all` 则变成只要有一条不合格就整批不写。

超过 100 条会自动分片，`write_plan` 里会给出每个分片文件。

### 第 3 步：写入前取基线

```bash
python3 scripts/append_guard.py capture --out /tmp/order-baseline.json
```

记录全表记录 ID 与字段值指纹，作为"原有内容未被改动"的证据。

### 第 4 步：追加写入

按 `write_plan` 逐个分片执行，这是全流程唯一允许的写操作：

```bash
dws aitable record create --base-id <baseId> --table-id <tableId> \
  --records-file <分片文件> --format json
```

从返回的 `data.newRecordIds[]` 取新增记录 ID。不要读取不存在的标量 `recordId`。

某一片失败时停止后续分片，不要重试到写入重复。

### 第 5 步：写入后复核

```bash
python3 scripts/append_guard.py verify \
  --baseline /tmp/order-baseline.json --expect-added <实际新增条数>
```

`unchanged=true` 才代表原有记录一条未变。出现 `missing` 或 `changed` 立即停止并如实上报。

再回读新增记录比对字段：

```bash
dws aitable record query --base-id <baseId> --table-id <tableId> \
  --record-ids <id1,id2> --field-ids <订单编号,下单日期,虚拟手机号,承接助教字段ID> --format json
```

日期字段回读是 RFC3339（如 `2026-09-11T16:05:04+08:00`），与 `2026-09-11 16:05:04` 属同一时刻，是正常的。

## 汇报格式

1. 本次承接助教是谁（必须是使用者本次指定的姓名）。
2. 新增几条、跳过几条（已存在）、阻断几条及原因。
3. 新旧记录数对比。
4. 原有记录未变动的校验结论。
5. 逐字段回读结果。

## 失败处理

| 情况 | 处理 |
|---|---|
| 未拿到助教姓名 | 立即追问，不要沿用历史值，也不要在追问期间执行任何写入步骤 |
| 助教名字查不到 | 停止，请使用者确认姓名 |
| 助教名字非完全匹配（模糊命中） | 停止，把语义检索给出的候选念给使用者确认，不要自行采用 |
| 助教同名的候选多于一个 | 停止，把候选列给使用者确认 |
| 预检阻断（字段类型/权限） | 停止，报告原因，等使用者处理 |
| 订单编号位数不对 | 阻断该条，请使用者核对截图，不要截断或补零 |
| 商品单ID 与订单编号不一致 | 阻断该条，可能识别串行 |
| 时间或号码无法识别 | 阻断该条，不要用相邻行的值填空 |
| 去重查询失败 | 停止整批，宁可不写也不能重复写入 |
| 写入部分失败 | 停止后续分片，保留失败明细 |
| verify 报出 missing/changed | 立即停止并如实上报 |

## 常见坑

- **订单编号精度**：文本字段是前提。历史上用数字字段存的订单号末位已被改坏，无法还原。
- **助教错配**：一张表里多个助教共用，写错人比漏写更难发现。所以助教必须显式指定。
- **视图筛选**：如果目标表里有按承接助教筛选的子视图，写入某位助教的记录不会自动出现在别人的筛选视图里，只在不带该筛选的视图可见。
- **人员字段**：助教必须是当前组织内唯一匹配，跨组织写入会失败。
- **虚拟号有效期**：通常 29 天，过期需重新申请。表里存的是虚拟号，不是真实手机号。
- **敏感信息**：截图与写入内容含姓名、手机号，属于个人信息，需控制表格共享范围。

## 资源

- `references/target-table.json` — 目标表与字段配置，换表只改这里；`defaults.assistantName` 仅作追问话术示例，不是可自动生效的默认值
- `references/extraction-rules.md` — 截图读取与取值规则
- `scripts/preflight_check.py` — 只读预检
- `scripts/validate_records.py` — 提取结果校验、去重与分片
- `scripts/append_guard.py` — 只增不改的写入前后守卫

两个脚本在缺助教时都会返回 `next_action: ask_user_for_assistant`，这是要求追问的信号，不是可以忽略的告警。
